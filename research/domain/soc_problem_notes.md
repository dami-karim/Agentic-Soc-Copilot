# The SOC Problem — Domain Foundation Notes

## What is a SIEM?
A Security Information and Event Management (SIEM) system centralizes log data from across an organization's environment — endpoints, network devices, cloud services, identity providers — into one searchable index, and lets analysts write queries (rules) that fire alerts when patterns match known-bad or suspicious activity. Examples: Splunk (SPL), Elasticsearch (Lucene/KQL-style), Microsoft Sentinel (KQL). A SIEM does *detection and search*; it does not investigate or respond on its own — that's the analyst's (or agent's) job.

## What does a Tier-1 analyst do every day?
- Reviews the queue of alerts generated by SIEM correlation rules
- For each alert, performs initial triage: is this a true positive or false positive?
- Pivots across related data sources to gather context (check IP reputation → check logon history → check if a successful logon followed a failed one → check for lateral movement)
- Escalates confirmed or ambiguous incidents to Tier-2/Tier-3 analysts for deeper investigation
- This work is repetitive, high-volume, and — per industry reporting — analysts estimate a large majority of daily alerts turn out to be false positives, which is the direct cause of alert fatigue.

## Why is alert fatigue a problem?
When analysts see mostly false positives, vigilance and response quality degrade — real threats get missed or deprioritized simply because they arrive indistinguishable from noise. This is a documented driver of analyst burnout and turnover, which further degrades SOC effectiveness (loses institutional knowledge, increases training overhead).

## What is MTTR / MTTD?
- **MTTD (Mean Time to Detect):** the average time between when a compromise begins and when it is identified.
- **MTTR (Mean Time to Respond/Remediate):** the average time between detection and full containment/remediation.
- Industry reporting (e.g., IBM's annual Cost of a Data Breach Report) consistently shows these two metrics as strong predictors of total breach cost — organizations that detect and contain faster lose significantly less money and data. This is the quantitative justification for automating triage: shrinking MTTD/MTTR is the entire point of an agentic SOC.

## Sample annotated alert (illustrative — replace with actual BOTS v3 field values once the dataset is downloaded)
```json
{
  "host": "web-fro-r01",
  "src_ip": "192.168.250.100",
  "dest_ip": "192.168.250.20",
  "EventCode": "4625",
  "sourcetype": "WinEventLog:Security",
  "severity": "medium"
}
```
- `host` — the machine that generated the log entry (here, the destination host being logged into)
- `src_ip` — where the logon attempt originated from
- `EventCode` — the Windows Security Event ID; **4625 = failed logon attempt**, 4624 = successful logon
- `sourcetype` — tells the SIEM which parser/schema to apply to this log line
- `severity` — the SIEM's own risk scoring for this event, usually derived from a correlation rule, not the raw log itself

**What would a Tier-1 analyst do when they see this alert?**
1. Check `src_ip` reputation (internal vs. external, known-bad list, geolocation if external)
2. Check logon history for the target account/host — is repeated 4625 normal for this asset (e.g., a scheduled job with stale credentials) or new?
3. Check whether a successful logon (4624) followed the failed attempts from the same `src_ip` shortly after — this is the strongest single signal of a successful brute-force
4. If a successful logon followed, check for lateral movement (new sessions from the compromised host to other internal hosts)

This exact pivot sequence — reputation → history → correlation → lateral movement — is what the agent's tool-calling loop needs to replicate.
